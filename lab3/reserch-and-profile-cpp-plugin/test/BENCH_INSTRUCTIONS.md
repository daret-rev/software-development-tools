# Инструкция по автоматическому исследованию производительности

Документ описывает, какие консольные команды выполнять, в каком порядке, какой вывод ожидать и что из него брать в итоговый отчёт. Он основан на `PROFILING.md`. Все команды рассчитаны на Linux.

## Обозначения

| Метка | Смысл |
|-------|-------|
| `<exe>` | имя исполняемого файла проекта (например, `WordCount`) |
| `<args>` | аргументы программы (например, `-l -w -c`) |
| `<data>` | файл или папка с тестовыми данными |
| `<N>` | число повторов (рекомендуется 5) |
| `<commit>` | хеш коммита |

Значения в блоках «Пример вывода» выдуманные, они показывают только формат.

## Правила для всех блоков

1. Код возврата команды проверять всегда. Ненулевой код означает ошибку блока.
2. Вывод хранить полностью (stdout и stderr отдельно), в отчёт попадает только извлечённое.
3. Если блок завершился ошибкой, дальнейшие блоки, зависящие от него, пропускаются, а в отчёте пишется причина.
4. Числа сравнивать как числа, а не как строки: пробельное выравнивание в выводе `wc` и `perf` разное.

## Блок 0. Предварительные условия

```shell
sudo pacman -S --needed perf time cmake clang lld git
```

На других дистрибутивах пакеты называются иначе, смысл: нужны `perf`, GNU `time` (файл `/usr/bin/time`), `cmake`, `clang`.

Проверка наличия:

```shell
command -v perf cmake clang++ git /usr/bin/time
```

**Ожидаем:** пять строк с путями. Если какой-то нет, блок заваливается.

## Блок 1. Окружение

### Команды

```shell
uname -r
lscpu
nproc
free -b
findmnt -T <data> -o SOURCE,FSTYPE
lsblk -d -o NAME,ROTA,SIZE,MODEL
clang++ --version
cmake --version
perf --version
cat /proc/sys/kernel/perf_event_paranoid
```

### Пример вывода

```text
6.6.50-1-MANJARO
Model name:          AMD Ryzen 7 5800H
CPU(s):              16
Thread(s) per core:  2
L1d cache:           256 KiB (8 instances)
L2 cache:            4 MiB (8 instances)
L3 cache:            16 MiB (1 instance)
16
Mem:    16513441792  ...
SOURCE FSTYPE
/dev/nvme0n1p2 ext4
NAME    ROTA SIZE   MODEL
nvme0n1    0 476.9G Samsung SSD 980
clang version 19.1.7
cmake version 3.31.2
perf version 6.6.50
2
```

### Что извлекать

| Поле отчёта | Откуда |
|-------------|--------|
| Ядро ОС | `uname -r` целиком |
| Процессор | значение после `Model name:` |
| Потоков | значение после `CPU(s):` или `nproc` |
| Кэш L1d, L2, L3 | значения после `L1d cache:` (в новых версиях `L1d:`), `L2 cache:`, `L3 cache:` |
| ОЗУ, ГБ | второй столбец строки `Mem:` из `free -b`, делится на 2^30 |
| Диск | строка `lsblk` для устройства из `findmnt` (устройство `nvme0n1p2` соответствует диску `nvme0n1`) |
| Тип диска | `ROTA` равно 0: SSD/NVMe, равно 1: HDD |
| Компилятор | первая строка `clang++ --version` |
| CMake | первая строка `cmake --version` |
| perf | вывод `perf --version` |
| paranoid | число из последней команды |

### Условие

Если `perf_event_paranoid` больше 1, счётчики блока 5 могут не заработать. Тогда:

```shell
sudo sysctl kernel.perf_event_paranoid=1
```

Значение сбрасывается при перезагрузке. В отчёте указать, что оно было изменено.

## Блок 2. Данные

### Команды

```shell
du -sb <data>
find <data> -type f | wc -l
```

Если `<data>` это один файл:

```shell
stat -c %s <data>
```

### Пример вывода

```text
53687091200	/data/corpus
355
```

### Что извлекать

| Поле | Откуда |
|------|--------|
| Размер данных, байт | первое число `du -sb` (или `stat`) |
| Размер, ГиБ | размер, делённый на 2^30 |
| Число файлов | вывод `wc -l` (для одного файла 1) |

## Блок 3. Сборка

### Команды

```shell
git rev-parse --short HEAD
git log -1 --format=%s
cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build -j
find build -type f -name <exe> -perm -u+x
```

`RelWithDebInfo` соответствует флагам `-O2 -g` из `PROFILING.md`.

### Ожидаем

- Все команды заканчиваются с кодом 0.
- Последние строки сборки содержат `Built target <exe>` (генератор Makefiles) или `ninja: no work to do` / строки `[N/N]` (Ninja).
- `find` выводит ровно одну строку, путь к исполняемому файлу. Ноль строк: цель не найдена, блок заваливается. Больше одной: брать первую и записать предупреждение.

### Что извлекать

| Поле | Откуда |
|------|--------|
| Хеш коммита | первая команда |
| Описание коммита | вторая команда |
| Путь к программе (`<exe_path>`) | вывод `find` |

## Блок 5. Время и память

### Подготовка

Холодный запуск (кэш ОС сброшен):

```shell
sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'
/usr/bin/time -f "%e %U %S %M" <exe_path> <args> <data> > /dev/null
```

Тёплые запуски (кэш заполнен) повторяются `<N>` раз:

```shell
/usr/bin/time -f "%e %U %S %M" <exe_path> <args> <data> > /dev/null
```

То же для эталона:

```shell
LC_ALL=C /usr/bin/time -f "%e %U %S %M" wc -l -w -c <data> > /dev/null
```

### Пример вывода (stderr)

```text
11.37 38.21 1.04 71204
```

### Что извлекать

Четыре числа в строке: секунды реального времени (`%e`), время в пользовательском режиме (`%U`), время в ядре (`%S`), пик памяти в КБ (`%M`).

| Поле | Как считать |
|------|-------------|
| Время (холодный) | `%e` одного холодного запуска |
| Время (тёплый), мин | минимум `%e` по тёплым запускам |
| Время (тёплый), медиана | медиана `%e` по тёплым запускам |
| Загрузка процессора | `(%U + %S) / %e`: значение около числа потоков означает хорошую параллельность |
| Пик памяти, МБ | `%M` делится на 1024 |
| Скорость, ГБ/с | размер данных из блока 2, делённый на минимальное время |

Для `wc`, если папка из нескольких файлов, команда выполняется по списку файлов, как у собственной программы.

## Блок 6. Аппаратные счётчики

### Команда

```shell
perf stat -r <N> -x, -e cycles,instructions,branches,branch-misses,cache-misses -o stat.csv -- <exe_path> <args> <data>
```

### Пример stat.csv

```text
# started on Sun Oct 11 01:20:00 2026

1204551233,,cycles,1500000,100.00,,
3500777777,,instructions,1500000,100.00,2.91,insn per cycle
512000000,,branches,1500000,100.00,,
5100000,,branch-misses,1500000,100.00,1.00,of all branches
8300000,,cache-misses,1500000,100.00,,
```

### Формат строки

Поля через запятую: значение, единица, событие, время работы счётчика, доля времени, производная метрика, её описание.

- Строки с `#` и пустые пропускать.
- На процессорах с разными типами ядер имя события выглядит как `cpu_core/cycles/`, нужно сопоставлять по вхождению (`cycles`, `instructions`, `branches`, `branch-misses`, `cache-misses`).
- Значения `<not supported>` и `<not counted>` означают, что счётчик недоступен. В отчёт пишется `н/д`.
- Если вывод `-r` содержит среднее по запускам, брать его.

### Что извлекать и считать

| Поле | Формула |
|------|---------|
| Такты | `cycles` |
| Инструкции | `instructions` |
| IPC | `instructions / cycles` |
| Ветвления | `branches` |
| Промахи ветвлений | `branch-misses` |
| Доля промахов ветвлений, % | `100 * branch-misses / branches` |
| Промахи кэша | `cache-misses` |

### Условие

Если `perf` завершился с ошибкой доступа (`Permission denied`, `You may not have permission`), проверить `perf_event_paranoid` (блок 1). Если счётчики недоступны совсем (например, в виртуальной машине), колонки отчёта заполняются `н/д`, остальные блоки выполняются.

## Блок 7. Профиль: где тратится время

### Команды

```shell
perf record -g -o perf.data -- <exe_path> <args> <data> > /dev/null
perf report -i perf.data --stdio --no-children --percent-limit 1 2>/dev/null
```

### Пример вывода report

```text
# Overhead  Command    Shared Object  Symbol
# ........  .........  .............  ......
    71.20%  WordCount  WordCount      [.] CountElements
    12.40%  WordCount  libc.so.6      [.] read
     3.10%  WordCount  [kernel]       [k] copy_user_enhanced_fast_string
```

### Что извлекать

- Строки, которые начинаются с пробелов и числа с процентом. Строки с `#` пропускать.
- Из каждой строки: процент, символ (последнее поле после `[.]` или `[k]`), признак `[.]` (пользовательский код) или `[k]` (ядро).
- В отчёт попадают первые 5 строк.

### Как читать

Если доминирует функция подсчёта, программа упирается в вычисления. Если растёт доля ядра (`[k]`) и `read`, программа упирается в ввод-вывод.

## Блок 8. Санитайзеры

### Команды

```shell
cmake -S . -B build-tsan -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_COMPILER=clang++ -DCMAKE_CXX_FLAGS="-fsanitize=thread -g" -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=thread"
cmake --build build-tsan -j

cmake -S . -B build-asan -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_COMPILER=clang++ -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -g" -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
cmake --build build-asan -j

TSAN_OPTIONS=halt_on_error=1 <exe_tsan_path> <args> <data> > /dev/null
ASAN_OPTIONS=detect_leaks=1 <exe_asan_path> <args> <data> > /dev/null
```

Пути `<exe_tsan_path>` и `<exe_asan_path>` ищутся тем же `find`, что в блоке 3, но в папках `build-tsan` и `build-asan`.

Для санитайзеров лучше взять небольшой набор данных (медленнее в 2-10 раз) из нескольких десятков файлов, чтобы потоки конкурировали.

### Ожидаем

- Код возврата 0.
- В stderr нет строк `WARNING: ThreadSanitizer`, `ERROR: AddressSanitizer`, `runtime error:`, `LeakSanitizer`.

### Что извлекать

| Поле | Значение |
|------|----------|
| Thread | `ЧИСТО`, если выполнены условия выше, иначе `НАЙДЕНЫ ПРОБЛЕМЫ` и первая строка предупреждения |
| Address + Undefined | то же |

### Известная проблема TSan

На новых ядрах `ThreadSanitizer` может завершиться с сообщением `FATAL: ThreadSanitizer: unexpected memory mapping`. Это не ошибка программы. Лечится:

```shell
sudo sysctl vm.mmap_rnd_bits=28
```

После этого запустить блок заново.

## Блок 9. Прогон по истории коммитов

Выполняется для сравнения версий: каждый коммит проходит блоки 3-6.

### Команды

```shell
git rev-list --reverse HEAD
git log -1 --format=%s <commit>
git worktree add --detach <tmpdir> <commit>
git worktree remove --force <tmpdir>
git worktree prune
```

### Порядок

Для каждого `<commit>` из первой команды:

1. Создать рабочую копию (`worktree add`).
2. В ней выполнить блоки 3, 4, 5, 6.
3. Удалить копию (`worktree remove`).

### Условия

- Коммит без `CMakeLists.txt`: пропустить, в таблице строка `нет сборки`.
- Коммит, не прошедший блок 3 или 4: строка с причиной, остальные блоки для него пропускаются.
- Пути к данным в аргументах должны быть абсолютными, потому что копии лежат в других папках.

## Итоговый отчёт

Файл `RESEARCH.md`, собранный из результатов блоков.

### Структура

```markdown
# Исследование производительности <exe>

## Окружение
<таблица из блока 1>

## Данные
<таблица из блока 2>

## Результаты по версиям

| Версия | Корректность | Время, холодный, с | Время, тёплый (мин / медиана), с | ГБ/с | Загрузка CPU | Пик памяти, МБ | IPC | Промахи ветвлений, % | Промахи кэша |
|--------|--------------|--------------------|----------------------------------|------|--------------|----------------|-----|----------------------|--------------|
| <хеш и описание коммита> | ок / ОШИБКА | ... | ... | ... | ... | ... | ... | ... | ... |
| wc (LC_ALL=C) | эталон | ... | ... | ... | ... | ... | н/д | н/д | н/д |

## Профиль последней версии
<первые 5 строк из блока 7>

## Санитайзеры последней версии
<результат блока 8>

## Выводы
<заполняется вручную: что дало прирост, что нет, отвергнутые варианты>
```

### Правила заполнения

1. Строки таблицы идут в порядке коммитов от старого к новому. Строка `wc` идёт последней.
2. Числа округлять: время до 2 знаков, IPC до 2, проценты до 2, остальное целыми.
3. Недоступные значения помечать `н/д`.
4. В заголовок таблицы или под ней обязательно записать, был ли кэш холодным для колонки «тёплый» (нет) и «холодный» (да), и значение `perf_event_paranoid`, если оно менялось.
5. Раздел «Выводы» не заполняется автоматически: его пишет человек по таблице.
